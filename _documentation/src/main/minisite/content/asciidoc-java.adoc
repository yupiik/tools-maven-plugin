= Asciidoc Java
:minisite-index: 400
:minisite-index-title: Asciidoc Java
:minisite-index-icon: book
:minisite-index-description: Asciidoc Java native parser.

`asciidoc-java` is an AsciiDoc parser and two renderers written in plain Java, without JRuby.
It reads a document into a model you can walk, then renders that model as the HTML asciidoctor writes or as GitHub-flavored Markdown.
It needs no JRuby and depends only on `ascii2svg`, so it embeds in any Java application and runs in a native image.
It implements a large subset of AsciiDoc, with asciidoctor as the reference for what each construct gives.

The documentation of the module is split into pages:

* xref:asciidoc-java-syntax.adoc[Supported syntax]: the AsciiDoc and Markdown constructs the parser reads, the attributes that change how it reads them, and the known differences from asciidoctor.
* xref:asciidoc-java-html.adoc[HTML renderer]: `AsciidoctorLikeHtmlRenderer`, its options, the attributes it reads, icon fonts and slides.
* xref:asciidoc-java-markdown.adoc[Markdown renderer]: `GithubFlavoredMarkdownRenderer` and what each construct becomes in Markdown.
* xref:asciidoc-java-model.adoc[Model and visitors]: the parsed model, the `Visitor` contract, the readings the renderers share, source positions, and how to write your own renderer.

== Quick start

Parsing and rendering take three objects: a `Parser`, the `Document` it returns, and a renderer that visits the document.

[source,java]
----
final var parser = new Parser(); <1>
final var doc = parser.parse(myDocContent, new Parser.ParserContext(ContentResolver.of(Path.of("asciidoc/content")))); <2>
final var renderer = new AsciidoctorLikeHtmlRenderer(); <3>
renderer.visit(doc); <4>
final var html = renderer.result(); <5>
----
<.> Create a parser instance, it can be a singleton in an application,
<.> Load the document model, the `ContentResolver` says where `include::[]` targets are read from,
<.> Create a renderer, here the HTML one; its other constructors take a configuration, with attributes and options, and a `VisitorSibling`,
<.> Visit the document,
<.> Get back the output of the renderer, the HTML here.

TIP: the `Document` instance is thread safe and can be reused across threads, and so is the parser. A renderer is not: the HTML renderer keeps its output, so create one per rendering; the Markdown renderer starts from an empty output at each `visit`, so one instance renders documents one after the other in one thread.

The same document renders to Markdown with `GithubFlavoredMarkdownRenderer` in place of the HTML renderer, see xref:asciidoc-java-markdown.adoc[Markdown renderer].

== Where it is used

* The `minisite` goal of the Maven plugin renders the pages with this parser instead of AsciidoctorJ when `yupiik.minisite.preferYupiikAsciidoc` is `true`; the `yupiik-tools-cli` minisite command does the same with `--useYupiikAsciidoc`.
* The `asciidoc` goal of the Maven plugin renders one document with it and sets the renderer options with `yupiik.asciidoc.` properties, see xref:asciidoc-java-html.adoc#_configuration_options[the HTML renderer options]; with `yupiik.asciidoc.renderer` set to `shower` it renders a slide deck through the `ShowerRenderer`, see xref:asciidoc-java-html.adoc#_slides[Slides].
* Any Java application that embeds the module, as in the quick start above.

== Compatibility

asciidoctor is the reference: when the parser or a renderer reads a construct, the result is meant to be what asciidoctor gives for the same input, and the expected outputs of the tests are written from it.
The HTML renderer writes the markup asciidoctor's stylesheet expects, so that stylesheet applies to the output without changes, but byte-for-byte equality with asciidoctor is not a goal.

IMPORTANT: the AsciiDoc syntax is not 100% implemented yet. xref:asciidoc-java-syntax.adoc[Supported syntax] lists what the parser reads and the known differences from asciidoctor. If you miss a construct, open an issue or a pull request on the bugtracker.
