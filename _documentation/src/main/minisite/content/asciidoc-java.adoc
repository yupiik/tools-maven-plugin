= Asciidoc Java
:minisite-index: 400
:minisite-index-title: Asciidoc Java
:minisite-index-icon: book
:minisite-index-description: Asciidoc Java native parser.

The module `asciidoc-java` implements a light Asciidoc syntax parser in plain Java.
It aims at making it easier and lighter than using JRuby to embed Asciidoc in any Java based (native or not) application.

Its usage is pretty simple:

. You get a `Parser` instance to load the model of your document in memory (AST),
. You visit the model as you want (or reusing provided `Visitor<?>`) to render the loaded `Document`.

TIP: the `Document` instance is thread safe and can safely be reused accross multiple threads. The parser is also thread save but the visitors must be created per rendering instance.

Here is a basic example:

[source,java]
----
final var parser = new Parser(); <1>
final var doc = parser.parse(myDocContent, new Parser.ParserContext(ContextResolver.of(Path.of("asciidoc/content")))); <2>
final var renderer = new AsciidoctorLikeHtmlRenderer(); <3>
renderer.visit(doc); <4>
final var html = renderer.result(); <5>
----
<.> Create a parser instance, can be a singleton in an application,
<.> Load the document model, can also be a singleton in an application when the conditions depends on attributes,
<.> Create a renderer (here a html renderer, optionally you can pass it attributes using the other constructor),
<.> Visit the document,
<.> Get back the output of the renderer (html output here).

IMPORTANT: the asciidoc syntax is not 100% implemented yet, if you encounter anything you miss, feel free to open an issue or pull request on our bugtracker.

== Markdown output

`GithubFlavoredMarkdownRenderer` renders the same model as GitHub-Flavored Markdown, for example to publish a Markdown copy of a page for AI agents or to feed a text pipeline:

[source,java]
----
final var renderer = new GithubFlavoredMarkdownRenderer(new GithubFlavoredMarkdownRenderer.Configuration()
    .setAttributes(Map.of("imagesdir", "/images"))); <1>
renderer.visit(doc);
final var markdown = renderer.result();
----
<.> Pass the attributes the renderer uses when the document does not define them, as for the HTML renderer.

The Markdown renderer writes each construct as follows:

[options="header",cols="1,2"]
|====
|AsciiDoc|Markdown
|Section (`== Title`)|ATX heading (`## Title`).
|Source block|Fenced code block with the language. A diagram style such as `[mermaid]` is kept as the language.
|Table|Pipe table.
|Admonition|GitHub alert (`> [!NOTE]`).
|Callouts|Numbered list after the code block, the `<1>` markers staying in the code.
|Description list|Bold term followed by its description.
|Collapsible block (`[%collapsible]` or `opts=collapsible`)|`<details>` element.
|Footnote|`[^1]` reference, with its definition at the end of the document.
|Id of a section or of a block|Empty `<a id="...">` anchor, so `<<id>>` links work. A section without an explicit id gets the id the HTML renderer would give it when the document links to it.
|Table of contents (`:toc:`)|List of links to the sections, where asciidoctor places it: at the top, after the preamble (`:toc: preamble`) or at the `toc::[]` macro (`:toc: macro`).
|Icon (`icon:lock[]`)|`[lock]`, as asciidoctor writes an icon without an icon font.
|====

When neither the document nor the configuration defines an attribute, the Markdown renderer leaves its reference literal. An `include` macro reaching the renderer fails, since the parser resolves includes before rendering.

One renderer instance can render several documents one after the other: each call to `visit` starts from an empty output. A subclass can override any rendering method, and the override also applies inside admonitions, lists and tables.

The Markdown renderer reads these attributes:

[options="header",cols="1,2"]
|====
|Attribute|Use
|`noheader`|Skips the document title.
|`imagesdir`|Prefixed to a relative image target.
|`idprefix`, `idseparator`|Build the id of a section without an explicit id, as in the HTML renderer.
|`relfileprefix`, `relfilesuffix`|Build the target of an `xref:page.adoc[]` link, `relfilesuffix` defaulting to `outfilesuffix` and then to `.md`.
|`asciidoc-extensions`|Extensions of the documents an `xref:` link points at, `adoc,asciidoc` by default. A link to a file with another extension keeps the file name, and a file without extension before a `#` is a document, as in asciidoctor.
|`toc`, `toc-placement`, `toc-title`, `toclevels`|Write the table of contents, as in asciidoctor.
|====

== Reading the model in a visitor

A custom visitor can read the model as the Markdown renderer does, with two classes of `io.yupiik.asciidoc.renderer`:

[options="header",cols="1,3"]
|====
|Class|Use
|`VisitorSibling`|Reads the values the parser keeps as raw text: the id, the style and the options of a block, attribute references in titles, cross reference and image targets, macro labels such as the keys of `kbd:[]`, and where paragraphs end when the parser gives them as sibling elements. It has no state, so any visitor can create one.
|`VisitorState`|Keeps the state of a rendering: the attributes of the document then the fallback ones, the title of each section by id, the ids the document links to, the sections of the table of contents and the footnotes. The renderer calls its `visit` and `visitBody` methods, then queries it while it writes. Before any `visit` it reads the fallback attributes only, so a visitor can render a body alone.
|====

`new GithubFlavoredMarkdownRenderer(configuration, sibling)` takes a subclass of `VisitorSibling`, whose readings then apply to the renderer and to its state.

== Syntax

The parser supports standard Asciidoc syntax including:

* Headings (e.g. `= Document Title`, `== Section`)
* Paragraphs and text formatting (`*bold*`, `_italic_`, `+monospace+`)
* Unordered lists (`*`) and ordered lists (`.`)
* Links (`link:url[text]`) and images (`image:path[alt]`)
* Tables (`|===`)
* Source blocks (`[source,...]`)
* Admonitions (NOTE:, TIP:, IMPORTANT:, WARNING:, CAUTION:)
* Open/closed blocks, quote blocks, listing blocks, example blocks
* Macros (`image:`, `video:`, `audio:`, `icon:`, `btn:`, `kbd:`, `menu:`, `xref:`, footnote)
* Include directives with `tag`/`tags`/`lines`/`leveloffset`/`indent` filtering
* Conditionals (`ifdef::[]`, `ifndef::[]`, `ifeval::[]` with `else::[]`, `elsif::[]`), the inline form `ifdef::name[content]` and multi-attribute conditions (`name1,name2` for an or, `name1+name2` for an and)
* Attributes and substitutions (`:name: value`, `{name}`, `:!name:` to unset, `\{name}` escaping)
* Callouts, footnotes, index terms, counters
* Table features: colspan, rowspan, header option, autowidth, stripes, column alignment
* Nested ordered/unordered lists, `[start=NN]` on ordered lists, `[qanda]`/`[horizontal]` description lists
* Video macros for YouTube/Vimeo embed, audio/video with controls
* Man page doctype (`= commandname(1)`)
* Document authors, either with the author line (`firstname middlename lastname <mail>`, multiple authors being separated by `;`, attribute entries being supported before it) or with attribute entries (`:author:`/`:email:` for a single author, `:authors:` or `:author_<n>:`/`:email_<n>:` for multiple ones)
* Revision line (`v1.0, 2013-01-01: the remark`, a revision number without a date requiring the `v` prefix)
* Author and revision attributes deduced from the header (`authorcount`, `authors`, `firstname`, `middlename`, `lastname`, `authorinitials`, `revnumber`, `revdate`, `revremark` and their `_<n>` variants), the attribute entries of the document winning over the values deduced from the author line, `Author` also exposing the deduced names
* Markdown pipe tables (`|---|`)
* Bibliography/glossary entries (`[[[ref]]]`)
* Bare email autolink (`user@example.com`)
* Inline STEM (`$...$`, `stem:[...]`)
* Block STEM (`[stem]`, `[latexmath]`, `[asciimath]` + passthrough)
* Section numbering (`:sectnums:`), special sections (`[appendix]`, `[bibliography]`, `[glossary]`, `[index]`)
* Inline role `[.role]#text#`, `%` option prefix
* TOC placement macro `toc::[]`, Mermaid diagrams

IMPORTANT: as in asciidoctor the document header ends on the first empty line so the line following the title is always the author line, a section or a list not preceded by an empty line becoming an author.

=== CommonMark syntax

The parser also supports a subset of CommonMark syntax for convenience:

* `**bold**` → bold text
* `~~strikethrough~~` → strikethrough text
* `` `code` `` → inline code
* `[text](url)` → inline links
* `![alt](url)` → inline images
* `# Heading` → section headings (level based on `#` count)
* `---`, `***`, `___` → horizontal rules
* `|---|` → pipe tables (Markdown table syntax)
* `**** content ****` → sidebar block
* Trailing double space at end of line → hard line break (`<br>`)

These syntaxes are recognized alongside native Asciidoc syntax and can be mixed freely.
